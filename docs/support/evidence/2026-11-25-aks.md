# AKS, 2026-11-25: the install proof (S87-13)

What `tools/cluster-proof/proof.sh` recorded on its third run, from a clean install of the chart of
branch `claude/wonderful-fermi-617o2f` (chart 0.29.4 with S87), `values/all-in-one.yaml` then
`values/aks.yaml`. The cluster was created by hand for the proof and deleted after it:

```
az aks create -g tranibor-s87-proof -n tranibor-s87-aks -l francecentral --kubernetes-version 1.35 \
  --os-sku AzureLinux --workload-runtime KataVmIsolation --node-vm-size Standard_D4s_v3 --node-count 2 \
  --network-plugin azure --network-plugin-mode overlay --network-dataplane cilium --tier free
az aks approuting enable -g tranibor-s87-proof -n tranibor-s87-aks
```

The site's domain was the ingress IP under nip.io, over http; the agent of the work item is the demo
project's simulated one, as in the single-node proof (no model is called).

## The same cluster, beside the proof

- `tranibor cluster check` (S87-03): every applicable check passed (Kubernetes v1.35.9, `kata-vm-isolation`,
  the default StorageClass, NetworkPolicy enforced in 3.5 s, the egress gate closed in 3.5 s).
- Tekton Pipelines v1.6.0 installed on it: `tests/cluster/test_tekton_isolation.py` under
  `kata-vm-isolation`, with Tekton's sidecars and with `enable-kubernetes-sidecar: true`, ended `Succeeded`
  both times, the agent's sidecar as uid 1001 finding no run token (S87-06).

## Not proven here

Signing in through the realm in a browser; a real model; a backup and restore (the backup pod mounts the
embedded volumes beside their owners, which a two-node cluster may refuse); the agent-sandbox executor
(the profile uses `k8s_job`); the object store with an Azure identity (S87-17 is proved on Azurite only).
